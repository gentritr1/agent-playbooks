# node-postgres failure paths, and PGlite as the test database

**Source:** tondo branch `crew-retention` (2026-10-10): `server/db.js`, `server/migrate.js`, `test/db.test.mjs`, `test/helpers/pg.mjs`; ledger and reports in `.superpowers/sdd/2026-10-10-crew-retention/` (`progress.md`, `task-3-report.md`, `task-4-report.md`, `task-5-report.md`, `final-fix-report.md`); commits `88230f9`, `1454033` (Task 3 and its fix round), `fa6a556` (client timeouts); installed `pg` 8.23.1 and `pg-pool` 3.14.0 (`node_modules/pg-pool/index.js`, read 2026-10-10). Every run below is against PGlite 0.5.8 behind `@electric-sql/pglite-socket` 0.2.11; nothing here ran against Neon (the project's live Neon task had not started).

## Measured (each by a test plus a mutant that removes the fix)
- **A checked-out client needs its own `'error'` listener.** The pool had `pool.on('error', …)` from the first commit. Mutant M1 (remove `client.on('error', onErr)` in `tx()`) failed the dropped-connection test with "uncaught exception: Connection terminated unexpectedly". pg-pool attaches its idle listener only while a client sits idle and removes it on checkout (read in `pg-pool/index.js`), so the pool listener does not cover a client in use.
- **After a drop the pool recovers by itself.** With the listener, the test destroys the socket mid-transaction: the call rejects with the store's own error, no uncaught exception, and the next query succeeds without a restart, "even with `TONDO_DB_POOL_MAX=1`" (`task-3-report.md`). pg-pool drops a client whose `_queryable` is false on release.
- **`statement_timeout` does not bound a silent socket.** Every `tx()` begins with `SET LOCAL statement_timeout = '3s'`, but the server enforces it, so a query that never reaches the server waits on the client. Test: a TCP proxy in front of PGlite that can be frozen (sockets open, nothing flows). Without `query_timeout: 5000` the request "did not finish within 9000ms"; with it, the call must reject with reason `timeout` in 4.5–7.0 s.
- **After a client read timeout, do not ROLLBACK on that client.** With the option added and `tx()` unchanged, the frozen-proxy call "failed too (took ~10 s)": the ROLLBACK queued behind the stuck query and waited out a second full timeout, and the dead client went back to the pool. The fix skips ROLLBACK after a "read timeout", and releases the client destroyed (`client.release(true)`) after a read timeout or a failed ROLLBACK.
- **Boot must not wait forever on the migration lock.** `start()` races each migration attempt against a deadline (60 s default); mutant M2b (no race) failed "start() did not finish within 2000ms" against a migration that never answers. The migrator sets `lock_timeout = '10s'` and `statement_timeout = '30s'` before `pg_advisory_lock`, and its `query_timeout` is 35 s, above its own statement limit. The test proves only that the two SETs are sent before the lock; that `lock_timeout` bounds a held advisory lock is UNVERIFIED, because PGlite cannot hold a lock from a second connection.
- Mutant counts: Task 3's fix round, 13 mutants, all caught; the timeout fix, the `query_timeout` deletion caught (the request hangs).

## PGlite through pglite-socket (what it can and cannot test)
- **One connection at a time.** The Task 3 spike printed "second connection: read ECONNRESET": a second concurrent connection is reset, not queued. Every PGlite-backed process runs with pool max 1 (`TONDO_DB_POOL_MAX=1`), and a test hands the database to another process (a spawned server, a direct client, the migrator) only after `await pool.end()` (tondo's `db.stop()`).
- **One session for all connections.** The migrator's session-level `SET statement_timeout = '30s'` leaked into later connections (seen as `30s` when the `SET LOCAL` was mutated away). On a real server each connection has its own session, so tests that read session settings pass or fail for the wrong reason.
- **Teardown order.** A SIGTERM'd server that exited with its connection half-closed crashed the PGlite test process intermittently (1 of 3 runs, a TypeError in pglite-socket's close handler after `db.close()`); the server now awaits its pool's close, and the test pauses 150 ms before stopping PGlite.
- **Out of reach:** `SELECT … FOR UPDATE` contention (two transactions cannot contend on one connection), Neon's pooler, TLS and wake from suspend. The ledger keeps them UNVERIFIED for the live Neon task.
- Related, another project: wordle runs its Neon serverless-driver SQL against WASM Postgres through a fetch shim that serialises statements, so interleaving is unproven there too ([neon](neon.md)).
